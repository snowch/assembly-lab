# Whole-course review: how much learners handle at once

Review snapshot: `f1fdf35eeee46f16edcf92e7738fe3dc77cf5583` (main), 23 October 2026. Scope: all 26 lessons, Modules 0–12 and optional A. This is an instructional design review. No course content, interface, simulator or deployment was changed.

## Judgement

There are other places worth simplifying. The strongest recurring evidence is **split attention**: sensible mechanisms are taught through large displays that learners must mentally reconnect. There are also candidates for smaller first applications before composition, especially the opening and field-writing activities. Those are design hypotheses with weaker evidence than the reproducible display and ordering issues.

My design direction is to give a new mechanism a small first application before demanding a larger composition. Related mechanisms can still be taught together. That does not mean one opcode per lesson. Compare/condition/select form a useful causal chain; loops and recursion should eventually combine familiar instructions; the bootable assembly capstone belongs at the end. Keeping later work permanently at single-instruction scale would remove useful transfer practice.

One proposed opening prototype is a short sequence: one addition with visible inputs and destination → reusing a destination as an input → subtraction → sequencing and the next-instruction marker → argument/result conventions and return → the complete C/assembly function. Retain a brief motivating whole-function overview, but move the sustained whole-function tracking to the point where those pieces are familiar. This is a design recommendation grounded in the user's repeated phone examples and the reviewed interface, not a measured learning-outcome claim.

## Ranked recommendations

1. **Opening lesson: prototype operation-first learning.** Use a small addition activity before sustained tracking across the whole function. Follow it with read-before-write, subtraction, sequence, and argument/return conventions. Keep the full function as the payoff. Priority reflects the user's repeated observed difficulty; independent readers did not establish that the current prediction prevents progress.
2. **Masks and fields: put practice before composition.** Move the existing basic-rule experiment before field extraction. Before unrestricted field replacement, give a bounded attempt at replacing an in-range field; make out-of-range source containment the next extension. The experiment placement is a concrete sequencing issue; staging the construction is a design priority rather than a proven first-attempt blocker.
3. **Memory and stack views: reduce bookkeeping.** The same shared pattern affects first loads, extension, array addressing, strings, calls and recursion. At phone width an array addressing figure is about 2,267px high and the four-frame recursion view about 4,334px. Their controls, relevant values and byte detail are far apart. Retain explicit addresses and data movement, but compare compact matched states; make unchanged bytes and per-frame byte expansion optional. Recursion needs visible call identity and saved values more than dozens of zero-byte cards.
4. **Boot chapter: stage the new environment.** Show file-to-memory placement when inspecting the linker script, and the startup recording when tracing entry/stack/storage. Trial a first pass that reaches a working boot with the supplied output routine, followed by inspection of serial polling, device setup and firmware differences. This broader staging is a design proposal; the supplied routine already permits a first boot. Preserve the assembly-only bootable program and its familiar arithmetic; device specifics are the new burden. In the debugging lesson, split the first GDB block into connect/entry, marker, prepared startup and function-input checkpoints, with interpretation beside each. Link the requested startup figure in the preceding lesson directly.
5. **Separate execution moments and explanations.** The multiplication chapter's completed product diagram and independently stepped registers need an explicit relationship. Branches should defer compiler source-attribution detail until after branch mechanics. A local four-rule key would also reduce reference travel in the flag exercise; that is a lower-priority aid. The overflow chapter should expose both instruction sequences during compiler-contract comparison; optional A32 exercises should keep the required recorded excerpt near their answer fields. These are targeted changes; they do not justify a whole-course rewrite.

Checked arithmetic is a further candidate for a clearer main path: conversions/promotion → range check → checked addition, with formatting and sanitizers as a separate follow-on. This is a design proposal rather than an established first-attempt blocker. The proposed wholesale multiplication reorder is also unconfirmed: its current low-product/MADD construction is reasonably bounded.

A successful production build established the reviewed artifact. No external compiler requests were needed. This was not a timed novice study, exhaustive state/input test or fresh ISA correctness audit. Known C, hexadecimal, register widths, branches and loads are credited once taught. A first prediction can legitimately elicit a best guess: any-answer commitment is not a retry-until-correct barrier. Worked rules before a transfer question are not automatically spoilers. Figure counts and page length are not findings on their own.

## Shared presentation direction

Keep the current instruction, action and relevant changed state close together. Trial decimal-first register summaries when the task is counting iterations or following calls; expose bits when bit patterns are the subject. This is a presentation option, not a confirmed flaw in every bit display. For byte transfers, show a compact source-to-destination mapping, with untouched memory and full inspection available on demand. When comparing addressing or extension choices, use a common source and matched result positions instead of several tall independent steppers.

The project currently requires complete numbered C beside associated instructions at every width (`CLAUDE.md:111`, `docs/visual-language.md:38`). On phones that pair is horizontally contained and initially exposes C. Hiding C in existing paired examples would be a policy change. An assembly-only primitive activity can teach an operation without inventing C; retain the complete paired program for synthesis. No such policy or implementation change was made in this review.
