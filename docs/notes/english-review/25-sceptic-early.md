# Sceptic assessment: English readers 00–12

18 October 2026. Review only; no learner-facing files changed. Model and effort inherited from the managing session; no override requested or applied. Independent assessment without author rationale. Read `CLAUDE.md`, both passes of `docs/style.md`, the thirteen reader notes, actual quoted source, lesson wiring where a referent depends on placement, shared strings and grader selection, and the preceding learner prose/prerequisite panel. Later teaching does not excuse earlier vocabulary. No replacement course prose or challenge answers are supplied.

**Disposition:** 22 reader findings become **18 accepted issues: 5 medium and 13 low**, after two duplicate merges and two rejections. Several medium reader ratings fall to low. Ranking reflects the likelihood of misunderstanding a mechanism or corrective instruction, not sentence length.

## Ranked accepted issues

### Medium

1. **Subtraction operand numbering conflicts with the established assembly convention** (04-1). `content/lessons/subtracting-and-the-tick-counter.prose.ts:42`: “the second operand, its bits changed”; `:100`: “an addition of the second operand with every bit changed, plus 1.” Module 0 explicitly says “An instruction's parts after its name are its operands” (`meet-the-machine.prose.ts:51`) and “It subtracts its third operand from its second” (`:65`). Therefore the reader has positive reason to identify the wrong source. The mathematical second input and assembly second operand need distinct references. Smallest fix: identify the subtracted input consistently in these two passages.

2. **The subtraction explanation calls a partial quantity the full sum** (04-2). `subtracting-and-the-tick-counter.prose.ts:41`: “Adding 1 gives 4294967296 minus `b` … This is the full sum”. The worked calculation at `:30–39` includes `a`, but this expression does not. The later `:78` correctly states “The adder adds `now` to `then` with every bit changed, plus 1”; it arrives after the construction. Smallest fix: distinguish the intermediate calculation involving `b` from the complete addition involving both inputs. Independently noticed extension: the reflection's `:100` also omits the first input altogether, even apart from its operand-number ambiguity. Repairing only the operand noun would leave an incomplete mechanism; include this in the same fix, not a new issue.

3. **Equal-input failure feedback diagnoses source selection misleadingly** (07-1). `compare-and-choose.prose.ts:74`: “Equal values give the wrong one. Which source does `csel` take when the condition is yes, and which when it is no?” `packages/views/src/grader-feedback.ts:118` selects this for failed equal arguments without establishing that the two selection sources still contain those arguments. Swapping two equal inputs cannot repair their value. Smallest fix: describe the failed returned value and direct inspection of the actual source contents, without implying one equal argument is the wrong choice.

4. **Hint headings call correct actions mistakes** (10-2 and 11-1, merged). `platform/lesson-runtime/src/strings.ts:122` fixes rung two as “Common mistake” and rung three as “Smaller example”. Against those headings, `counting-down.prose.ts:31` says “Put a label before the shift so a branch can repeat it”; `memory-and-addresses.prose.ts:34` says “Use the value in `w1` as the source and the address in `x0` as the destination”; `:59` says “Load four bytes from the address in `x0`.” These are recommended actions, so the heading can reverse their meaning for a struggling learner. The “Smaller example” mismatch (`memory-and-addresses.prose.ts:35`, for example) is lesser evidence of the same fixed-heading problem. Smallest fix: make affected rungs fulfil their headings, or use accurate headings through a supported mechanism. Do not edit the platform copy directly. One shared issue, not a separate medium for every lesson.

5. **The shift note relies on two unexplained C-rule categories** (06-1). `shifts.prose.ts:19`: “leaves the result … to the implementation”, “leaves some left shifts undefined”, and “GCC defines them”. The immediately preceding lessons explain GCC, optimisation and architecture, but never explain the difference between a compiler documenting a choice and C providing no guarantee. Repeated “defines” obscures that boundary; “a negative value among them” also attaches a value to a group of shifts. Smallest fix: identify the implementation and distinguish the two permissions in plain language, with the negative-input condition attached to its operation. No standards taxonomy lecture is needed.

### Low

6. **First prediction's execution point is implicit** (00-1, downgraded from medium). `meet-the-machine.prose.ts:34–35`: “Before you step through, commit to an answer” / “Where does the processor keep `total`?” The choice at `meet-the-machine.labels.ts:47`, “which now holds `leg1 + leg2`”, supplies substantial context, and the same register carries the calculation throughout. This is not a materially unanswerable prediction. Nevertheless entry state and the state after the first assignment are conflated. Smallest fix: identify the intended execution point in the question or setup without giving the location.

7. **“Set the flags” reuses a taught word in a different sense** (03-1, downgraded from medium). `adding-and-the-flags.prose.ts:70`: “Had `add` set the flags”. `one-pattern-three-readings.prose.ts:31` says “to set a bit is to make it 1”. The mixed values immediately following, and the earlier explanation at `adding-and-the-flags.prose.ts:14` that `adds` “records four facts”, make the intended sense recoverable. Still, contrasting “set” with “cleared” in the same paragraph unnecessarily makes this lesson's key distinction harder. Smallest fix: reserve setting/clearing for the bit values and use the established writing/recording language for all four flags.

8. **Dark-theme line marker is described as dark** (00-2). `meet-the-machine.labels.ts:36`: “the dark line-number chip”. Inspected the reader's actual rendered screenshot `/tmp/english00-step-1280-dark.png`: the selected marker is bright turquoise, whereas the unselected interiors are dark. Source wording therefore contradicts the displayed cue. Smallest fix: name a theme-independent property of the selected marker. No separate issue is needed for “chip”, whose visual referent is adjacent and clear.

9. **Shared simulator note introduces flags before their lesson** (00-3 and 01-1, merged). `packages/views/src/strings.ts:11`: “An instruction can read or change registers, flags or memory.” Front-page copy names flags but does not explain them. Module 0 explains registers and memory; the first real definition is `adding-and-the-flags.prose.ts:14`: “Each fact is stored in a flag: a single bit that is either 0 or 1.” That is too late for the earlier shared note. Smallest fix: constrain early note vocabulary or provide a minimal identification at first use. One shared issue across the early lessons.

10. **Prediction references overstate what code is displayed** (05-1, downgraded from medium). `masks.prose.ts:25`: “In this C”; `masks.labels.ts:69`: “the constant in the listing”. The source at `masks.prose.ts:26` actually supplies both the inline C statement and the compiled `and` instruction. Thus the reader does have the operation needed for the prediction: reject the implication that its essential code is absent. But `masks.ts:78–98` mounts no listing there, so its caption still directs a search for a displayed object that is absent. Smallest fix: identify the inline expression/instruction accurately; no additional full listing is necessary.

11. **Own-instruction figure is promised to show the warning word after every step** (05-2). `masks.prose.ts:65`: “the figure shows the word after each one”. The task at `:54` distinguishes warning word and new gear; the reader's recorded first step shows `w1 before` / `w1 after`. The figure can therefore show a gear intermediate instead. Smallest fix: describe the written register/value rather than promise the warning word each time.

12. **Application generalisation names representations without enough content to transfer the idea** (05-3). `masks.prose.ts:83`: “Status words, packed dates and colours keep several small numbers in one word in the same way.” Earlier lessons teach bits and arithmetic, not these representations; the prerequisite panel supplies none. “Several small numbers” connects the principle, but the reader cannot identify the constituent numbers in the named applications. Smallest fix: ground one application in its component values, rather than define all three labels.

13. **“This” seems to retract a GCC-output statement** (07-2). `compare-and-choose.prose.ts:125`: “GCC 16.1 at `-O1` did not use either in any listing here. This is not a claim about GCC's output.” The surrounding note does go on to hand-written instruction descriptions, but the nearest referent is explicitly a compiler-output claim. Smallest fix: name the scope of the qualification.

14. **Corrective feedback relies on an unexplained assembly grouping** (08-1). `branches.prose.ts:71`: “the next block … Does every block end in `ret` or `b`?” The preceding local definition at `:23` says a label “names the place of the instruction on the line below it”; it does not define the extent of a block. Searches of the preceding prose found no block definition. C braces do not establish the assembly unit. Smallest fix: refer to the labelled instruction groups and their execution order, or identify the intended grouping before relying on it.

15. **First noun use of trace is unexplained** (09-1). `counting-up.prose.ts:74`: “how many instructions it runs in one trace”. Earlier `meet-the-machine.labels.ts:43`, “the call to trace”, is a verb, not an explanation of the bounded sequence. The current sentence gives useful operational context, so this remains low; nothing warrants calling the loop explanation unusable. Smallest fix: identify what the trace records, or retain the already taught run vocabulary.

16. **Termination permission remains abstract in the optional C note** (10-1, downgraded from medium). `counting-down.prose.ts:60–61`: “assume termination” / “need not preserve a never-ending run”. The note already explains that input/output are effects beyond ordinary local changes, and explicitly ties its condition to `dim_wrong`. Reject the reader's stronger suggestion that these conditions are wholly ungrounded. It still does not translate the permission into an understandable consequence for generated code. Because the main paragraph already states exactly what the recorded GCC assembly does, this is a low issue in optional scope-setting, not a failure of the loop mechanism. Smallest fix: make the permitted consequence concrete without promising a particular other compiler's output.

17. **Memory reality note names an unexplained specialised C restriction** (11-2). `memory-and-addresses.prose.ts:71`: “C requires a valid object of a suitable type.” Local pointer teaching explains an address and the value reached through it, but no earlier text defines C object, validity or suitability here. Smallest fix: explain the relevant storage/type requirement at the scope of this example, not the full C memory model.

18. **Load reality note assumes structures and memory allocation** (12-1). `loading-widths.prose.ts:77`: “how every C compiler lays out a structure” / “managing memory allocation”. `apps/course/src/strings.ts:35` expressly says the learner need not know “pointers, structs, `malloc`”; pointers have since been introduced, structures and allocation have not. The local field list makes the exercise's record intelligible but does not supply these two concepts. Smallest fix: explain the limits using prepared memory and field positions, or identify the two concepts briefly. No structure syntax or allocation API is required.

## Rejected findings and merged records

- **02-1 rejected: bits versus set bits in the constants hint.** `constants-and-widths.prose.ts:53`: “a number whose bits fall in one 16-bit half” is a compressed restatement, but the lesson has already said at `:20`, “A single `mov` can load a constant whose set bits all fall in one 16-bit half. Some other patterns load too, so this is not the complete rule.” At `:19`, the concrete upper-zero example explicitly says “all its set bits are in the lower half”; `:28` again directs attention to “which halves … have set bits”. The claimed alternative interpretation requires ignoring that repeatedly taught criterion. No meaningful missing knowledge or mechanism error survives. Restoring “set” would be harmless polish, but is not a ranked fix.
- **03-2 rejected: “signed result does not fit” in the adder and reflection.** `packages/views/src/strings.arith.ts:92` uses conventional arithmetic-result language. Crucially, earlier `adding-and-the-flags.prose.ts:13` expressly separates the mathematical sum from kept bits: “If the sum of the two numbers is outside the signed or unsigned range, those bits cannot represent that sum under that reading.” Its prediction explanation at `:21` then demonstrates a stored pattern with a signed reading that is wrong for the intended sum. The reader has the exact missing distinction before the caption. The reflection `:105` also gives the signed arithmetic explicitly. Requiring every later result label to repeat this distinction is an overcall; the quoted caption does not claim that the bit pattern itself is invalid.
- **01-1 merged into issue 9**, with 00-3. Same shared sentence and same first-definition gap.
- **10-2 merged with 11-1 into issue 4.** Same fixed heading/content contract; memory's medium rating is justified for the combined issue. Other positive-action second rungs in these sources are covered by that shared repair direction, not new findings.

No finding was rejected merely because a reviewer already knew the term. Rejections above quote earlier teaching that supplies the claimed missing distinction. The low ratings for optional notes preserve their actual vocabulary gaps without claiming the main lesson mechanism depends on them.
