## c-and-overflow (Module 11, order 0)

Learning objective: separate C undefined behaviour from an A64 bit result, explain a deleted signed-overflow test, and guard before arithmetic.

1. Question: trip computer asks whether signed distance can increase. C `can_increment(distance)` returns `distance + 1 > distance`; recorded plain output is just `mov w0,1; ret`. Avoid overselling the output at INT_MAX as C's promised answer. The page begins with this actual listing.
2. Motivation: signed int selected target range -2147483648..2147483647, `INT_MAX` macro from limits.h. C places no requirements on overflowing signed addition, so valid inputs to this C expression satisfy distance+1>distance. GCC therefore emits constant true. Explain “undefined behaviour” plainly; it does not mean “random value” and a CPU does not know C types.
3. Prediction: course-authored `machine_increment: adds w0,w0,#1; ret`, input 2147483647. Ask final w0 bit pattern, options values `0x7fffffff`, `0x80000000`, `0x00000000`; choose correct position 2. It runs A64 directly, not the original C. Feedback may explain w0=0x80000000 and NZCV=1001 (N1 Z0 C0 V1), signed reading -2147483648. Stepper behind prediction shows w0 bits and flags.
4. Investigation: compare recorded plain and `-fwrapv` can_increment listings. The latter compares original distance with INT_MAX and returns ne; it need not literally add. Distinguish GCC option guarantee from C's standard rules.
5. Construction challenge `write-increment-limit`: signed distance arrives w0. Return 1 if distance==INT_MAX, else0. Scratch w1 permitted. Allowed mov/cmp/cset/ret. Reference mov w1,#2147483647;cmp w0,w1;cset w0,eq;ret. Six tests inputs [0,1,2147483646,2147483647,-2147483648,-1]; expected [0,0,0,1,0,0]. Labels tests must be6.
6. Failure experiment: same original C compiled with `-fwrapv`, input INT_MAX, predict boolean returned; values0,1 with correct0 at firstposition. Stepper illustrates compiler compares inputs, not “restoring” a particular arithmetic instruction. This is change in compiler assumption, not promise all compilers/flags do same.
7. Explanation: safe test uses operands/bounds before add. General signed addition preconditions: if b>0 then a>INT_MAX-b signals too high; if b<0 then a<INT_MIN-b signals too low. Those two bound subtractions fit when evaluated in their respective branches. Do not compute a+b then test it in ordinary signed C. Explain && short circuit if used.
8. Generalisation: new safe_increment C saturates at INT_MAX, otherwise +1; every signed input defined. Show recorded branch listing with exact extra compiler flags. Optional note relates INT_MIN negation and parsing: positive 2147483648 cannot fit int; a correct parser needs a wider type or checked negative accumulation, not negation after overflowing. No fabricated complete parser. Course-wide scenario crosswalk in engineering notes supports coverage; can give concise links to prior loops/division.
9. Final challenge `write-safe-increment`: same signed inputs as construction, return min(distance+1,INT_MAX) without adding at INT_MAX. Reference mov/cmp/b.eq/add/ret above; allowed mov,cmp,b.cond,b,add,ret. expected1,2,INTMAX,INTMAX,-2147483647,0. Six testlabels. State no instruction-execution grading? Tests inspect outputs; challenge contract explicitly asks before-add guard and reference models it, but output tests alone cannot reject a saturating implementation that safely uses architectural flags. Avoid claim grader proves absence of overflowing machine add: A64 wrap is defined.
10. Reflection: explain why inspecting one executable cannot determine all C guarantees. Ask why constant-return code is legal and why `-fwrapv` changes it. No claim small Module10 C compiler detects arbitrary C UB.
